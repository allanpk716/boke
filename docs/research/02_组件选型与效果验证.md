## ② 逐组件详述

### 1. VSE（YaoFANGUK/video-subtitle-extractor）——口碑真实但硬伤多

**效果证据：无公开基准数字。** 全网（含官方 README、PaddlePaddle 官方周刊推荐）都没有给出任何 OCR 准确率百分比、时间轴误差毫秒数的实测数据。README 只说"GPU 加速后可以获得更高的准确率与更快的提取速度"（[GitHub 仓库](https://github.com/YaoFANGUK/video-subtitle-extractor)，9.5k star）。这是"仅有社区口碑"的典型。

**项目状态：** 9,518 star，最新 release 2.2.0（2026-04-04），最后 push 2026-04-09，**263 个 open issue**。发版节奏：2023-10 v2.0.0 → 2025-04 v2.0.3 → 2026-04 v2.2.0，约一年一版，维护偏慢。

**Issue 区高频抱怨（按评论数排序，最能反映真实使用体验）：**

| 主题 | 代表 issue | 说明 |
|---|---|---|
| 时间戳不准 | [#144 精准模式时间戳不准（25 评论）](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/144)、[#67/#118/#128/#137/#325](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/325) | 时间轴错位/漂移是**贯穿 2021-2024 的持续性主题**，对本项目"字幕时间窗归人"是致命伤——时间窗错，归人就错 |
| 卡进度 | [#465 卡在94%（2026-08）](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/465)、[#443 卡在94%（2026-06）](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/443)、[#367 识别只输出7分钟](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/367) | **2026 年仍在发生**，且无权威修复答复 |
| 速度 | [#218 GPU 版 3 小时视频处理 6.5 小时才到 50%](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/218)、[#244 mac 50 分钟视频 4 小时](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/244)、[#294 GPU 占用<10%](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/294) | GPU 利用率低是常见病 |
| CUDA/Paddle 兼容 | [#232 cudnn 报错](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/232)、[#45 cudnn64_8.dll](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/45)、[#247 zlibwapi.dll](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/247)、[#355 paddle core 导入失败](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/355)、[#432 50系显卡不支持（2026-04）](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/432) | PaddlePaddle-GPU 版本和 CUDA/cuDNN 强绑定，是 issue 区第一大类；RTX 4090 没问题，但环境搭建摩擦大 |
| 丢字幕/识别不全 | [#141 快速模式丢字幕](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/141)、[#343 日文只能识别前几个字](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/343)、[#445 生成的字幕是空文件（2026-06）](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/445) | 快速模式靠跳帧，字幕停留短就丢；空文件问题 2026 年仍开放 |

**三模式差异**（README + 社区总结，无精确速度数字）：快速模式=跳帧检测，快但丢字幕（#141）；精准模式=逐帧检测，不丢但极慢（Softking 的 2.2.0 说明直接写"不推荐"）；自动模式居中。花字/艺术字/半透明字幕无专门的 issue 聚类——PaddleOCR 检测器本身对常规片源底部字幕够用，但台标误检类问题在 [#272 竖排文字过滤](https://github.com/YaoFANGUK/video-subtitle-extractor/issues/272) 等配置项里可间接佐证"非字幕区域误入"是真实存在的。

**和替代品对比：**
- **RapidVideOCR（SWHL）**：RapidOCR 系（PaddleOCR 模型转 ONNX，onnxruntime 推理），卖点是"配合 VideoSubFinder 抽关键帧"提速，2023 年后有 exe 版（[GitHub](https://github.com/SWHL/RapidVideOCR)）。部署比 Paddle 原生轻很多（不用装 paddlepaddle-gpu），但项目更新已趋缓，**适合当 OCR 引擎备选**。
- **VideOCR（timminator）**：793 star，**最后 push 2026-09-21（本周还在更新）**，GUI+CLI+Docker 三形态，本地 PaddleOCR 引擎（持续跟进 PaddleOCR 新版）+ Google Lens 混合模式，200+ 语言，CUDA 11.8（10系）/CUDA 12.9（16-50系）镜像齐全（[GitHub](https://github.com/timminator/VideOCR)）。 geeklink.dev 的横评称其为"Windows/Linux 最好的免费端到端硬字幕提取器"（[GeekLink 横评](https://geeklink.dev)）。
- **VideOCR 的上游就是 PaddleOCR 原生模型**，而 RapidVideOCR 是 ONNX 化的 PaddleOCR 模型——识别精度同级，差别在部署摩擦和更新活跃度。

**分级：有条件用偏避开（作为流水线核心组件）。** 理由：无基准数字 + 时间轴类 issue 持续五年 + 2026 年仍有"卡 94%/空文件"开放 issue + 一年一更。**建议：**
- 首选 VideOCR CLI（程序化调用友好、活跃、CUDA 12.9 镜像适配 4090）；
- 或自建"抽帧 + PaddleOCR PP-OCRv4/v5 中文模型 + 行稳定性合并"，自由度最高（见 ④ 调用建议）；
- VSE 可作为 GUI 交互式抽查的备用工具，不要绑进自动流水线。

### 2. pyannote speaker-diarization-community-1——放心用，数字齐全

**模型卡 DER 数字**（无 forgiveness collar、重叠语音计入，与 3.1 同口径对比，来源：[HF 模型卡](https://huggingface.co/pyannote/speaker-diarization-community-1)）：

| 基准集 | 3.1（legacy） | community-1 | 说明 |
|---|---|---|---|
| AISHELL-4（中文会议） | 12.2 | **11.7** | 中文 |
| AliMeeting ch1（中文会议） | 24.5 | **20.3** | 中文，远场 |
| AMI (IHM) | 18.8 | **17.0** | 会议采访类 |
| AMI (SDM) | 22.7 | **19.9** | 单通道远场 |
| DIHARD 3 (full) | 21.4 | **20.2** | 野采集采访 |
| MSDWild（中文野采重叠） | 25.4 | **22.8** | 中文+重叠语音 |
| RAMC（中文对话） | 22.2 | **20.8** | 中文 |
| VoxConverse v0.3 | 11.2 | **11.2** | 持平 |
| REPERE phase2 | 7.9 | 8.9（略退） | 唯一退步项 |
| CALLHOME part2 | 28.5 | **26.7** | 电话多说话人 |

（另有 precision-2 商用云版全面更低，如 AliMeeting 15.2、RAMC 10.5，但那是付费 API，不在本流水线范围。Earnings-21/Earnings-22 两个会议数据集在 community-1 模型卡上**未列出**，这是提问中提到但模型卡实际没有的——如实注明。）

**要点解读：**
- 对本项目最相关的就是中文会议/对话集（AISHELL-4、AliMeeting、RAMC、MSDWild），**全线提升 0.5~4.2 个百分点**；采访类（AMI/DIHARD）也稳定提升。
- **重叠语音**：基准评测明确"不跳过重叠段"（overlap 计入 DER）；社区版还输出了一个从商业版回移植的 "exclusive" 说话人轨，方便把分离时间戳和转写时间戳对齐。MSDWild 这种"中文野采重叠语音"集 25.4→22.8 说明重叠场景它见过、处理得了，但重叠段 DER 本质上仍是最难的部分（任何开源 diarization 在高重叠场景都掉点）。
- **说话人数**：不预设时用 `min_speakers`/`max_speakers` 给范围；已知人数直接 `num_speakers=N`。pyannote.ai 官方口径：community-1 相对 3.1 的主要进步点之一就是"说话人计数与归属"（[pyannote.ai 对比页](https://www.pyannote.ai)）。
- **与 NeMo Sortformer 对比**：Sortformer（NVIDIA）是端到端方案，强在流式/实时（[diar_streaming_sortformer_4spk-v2.1](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1)），但**硬上限 4 个说话人**，且 2025-09 的第三方横评结论是"PyannoteAI 开源版在离线基准上综合最优（约 11.2% DER 的量级领先），DiariZen 是开源竞争者"（[arXiv 横评 2025-09](https://arxiv.org)）。从业者反馈普遍是"NeMo 超参难调到超过 pyannote 开箱即用"。本流水线是离线批处理、说话人数不定 → community-1 是对的选。
- **访问流程（gated 但免费）**：模型 CC-BY-4.0，HF 页面登录接受条件（留联系方式）→ 到 hf.co/settings/tokens 生成 read token → `Pipeline.from_pretrained("pyannote/speaker-diarization-community-1", token=hf_token)`。离线机可 git lfs clone 到本地加载。
- **速度**：3.1 模型卡口径 RTF≈2.5%（V100，1 小时音频约 1.5 分钟）（[3.1 模型卡](https://huggingface.co/pyannote/speaker-diarization-3.1)）；CPU 则 RTF 0.5~1（1 小时音频 30-60 分钟）（[GitHub discussion](https://github.com/pyannote/pyannote-audio/discussions)）。community-1 换了更大的 embedding 模型（WeSpeaker），GPU 上同量级略慢，**务必 `.to(torch.device("cuda"))`**。4090 上富余。
- **WhisperX 默认集成核实**：WhisperX README 现已写明默认 diarization 模型就是 `pyannote/speaker-diarization-community-1`（需 HF token + 接受协议），CC-BY-4.0（[WhisperX README](https://github.com/m-bain/whisperX)）。**注意**：不少旧教程写的还是 3.1，以当前 README 为准。

**分级：放心用。** 失败模式：多人同时抢话段归属仍会错（归人后需要在 TTS 前人工抽查）；极短插话（<1s）容易被并进相邻说话人；音乐底噪大的采访建议先过人声分离再喂 diarization。

### 3. TTS 中文克隆横评（重点）

先给横评底表——**CosyVoice 官方 Evaluation 表**（[CosyVoice GitHub README](https://github.com/FunAudioLLM/CosyVoice)，Seed-TTS-Eval 口径，test-zh 用 CER%，SS=说话人相似度%）：

| 模型 | 开源 | 参数量 | test-zh CER↓ | test-zh SS↑ | test-en WER↓ | test-en SS↑ | test-hard CER↓ | test-hard SS↑ |
|---|---|---|---|---|---|---|---|---|
| Human（真人） | - | - | 1.26 | 75.5 | 2.14 | 73.4 | - | - |
| Seed-TTS（字节闭源） | ❌ | - | 1.12 | 79.6 | 2.25 | 76.2 | 7.59 | 77.6 |
| CosyVoice2 | ✅ | 0.5B | 1.45 | 75.7 | 2.57 | 65.9 | 6.83 | 72.4 |
| F5-TTS | ✅ | 0.3B | 1.52 | 74.1 | 2.00 | 64.7 | 8.67 | 71.3 |
| Index-TTS2 | ✅ | 1.5B | 1.03 | 76.5 | 2.23 | 70.6 | 7.12 | 75.5 |
| VoxCPM | ✅ | 0.5B | 0.93 | 77.2 | 1.85 | 72.9 | 8.87 | 73.0 |
| **Fun-CosyVoice3-0.5B-2512** | ✅ | 0.5B | **1.21** | **78.0** | 2.24 | 71.8 | **6.71** | 75.8 |
| **Fun-CosyVoice3-0.5B-2512_RL** | ✅ | 0.5B | **0.81** | 77.4 | **1.68** | 69.5 | **5.44** | 75.0 |

注意口径差异：IndexTTS-2.5 自己的技术报告（[arXiv:2601.03888](https://arxiv.org/abs/2601.03888)，Table 2）用 FunASR 算 WER（不是 CER）、SS 按 0-100 分，在它自己的评测协议下 IndexTTS2.5 中文 4.36/77.10、CosyVoice3-0.5B 3.84/80.01——**各家自评互有胜负，属于"评测协议不同各自领先"，但共同结论是：CosyVoice3 和 IndexTTS 系在中文第一梯队**。

#### 3.1 CosyVoice 2/3（FunAudioLLM，阿里）——克隆路线首选

- **硬数字**：上表。CosyVoice 3 论文（[arXiv:2505.17589](https://arxiv.org/abs/2505.17589) Table 4）口径：CosyVoice2 test-zh 1.45/0.748；CV3-0.5B 1.16/0.780；CV3-1.5B 1.12/0.781；RL 版 0.75/0.774。test-hard 6.83→5.09（RL），"接近人类录音水平"。跨语种 en2zh：CosyVoice2 13.5 WER → CV3-0.5B 8.48。
- **最新状态**：**Fun-CosyVoice3-0.5B-2512**（2025-12-16 开源，base+RL 两套权重，[ModelScope](https://modelscope.cn/models/FunAudioLLM/Fun-CosyVoice3-0.5B-2512) / [HF](https://huggingface.co/FunAudioLLM/Fun-CosyVoice3-0.5B-2512)），9 语言 + 18 中文方言，Apache-2.0，官方称中英混说 WER 相对 2.0 降低 56.4%（RL 口径）。
- **显存/速度**：0.5B 模型社区实测稳态显存 **4.1~4.3 GB**（[CSDN 实测](https://blog.csdn.net)），4090 上 RTF 可 <0.1（[知乎分析](https://zhuanlan.zhihu.com)）；但 RTF 口径混乱（vLLM 配置不当时有用户在 A100 测出 0.6+，[GitHub issue](https://github.com)），以自测为准。
- **社区对"像不像"的评价**：无单一权威评分，主流实测对比（[liudon 2026-05 五方案横评](https://liudon.com/posts/voice-cloning-solution-comparison)）结论：IndexTTS-2/CosyVoice/Fish Speech/VoxCPM 完成度都高，CosyVoice 速度居中（24 秒/句）；[ChatBlog 2026-08 横评](https://arch.gh.wzhecnu.cn/ChatBlog/blog/open-source-voice-cloning-frameworks-2025)给 CosyVoice 的定位是"**综合最均衡**：中文、多语、方言、服务化、长期维护都强"，"如果只选一个综合型项目，很可能就是它"。
- **失败模式**：**长文本直接合成会吞字/语音错乱**（约 50 字后可能触发，[GitHub issue #1532](https://github.com)），社区标准做法是**按标点分段合成再拼**——这正好契合配音场景（本来就是逐句合成）；vLLM 加速后曾有无意义噪音的已知问题（#1316），升级 vLLM ≥0.9/0.11 对应版本可解。

#### 3.2 GPT-SoVITS（RVC-Boss）——微调之王，zero-shot 无基准

- **版本争论结论**（官方 [features 文档](https://github.com/RVC-Boss/GPT-SoVITS) + 社区实测）：
  - 官方口径：v2Pro/v2ProPlus "**以 v2 的硬件成本和速度，达到超过 v4 的性能**"；
  - 训练集音质一般时，v1/v2/v2Pro 系表现稳，v3/v4 容易翻车；v3/v4 的语气音色更"贴"参考音频（zero-shot 特性强）；
  - v4 相对 v3 修复了金属音、原生 48k 输出；
  - **社区主流实测观点：v2ProPlus 是当前综合性价比最高的版本**（[知乎](https://zhuanlan.zhihu.com)、[腾讯云实战](https://cloud.tencent.com)："从 benchmark 跑分看，没有必要再用 V3 或 V4"）。
- **硬数字**：官方只给了速度，没给 WER/SIM 基准——v2ProPlus **RTF 0.028（4060Ti）/ 0.014（4090，1400 字约 4 分钟音频 3.36 秒合成完）**（[GPT-SoVITS README](https://github.com/RVC-Boss/GPT-SoVITS)）。克隆相似度**无公开基准，仅有社区口碑**：多篇中文实测（[dafei.me 2026-05](https://dafei.me) 等）认为"**GPT-SoVITS 是目前中文效果最好的开源方案，1 分钟数据微调即可高相似度**"——few-shot 微调路线的相似度口碑确实第一，但 zero-shot 直克隆不如 CosyVoice3/IndexTTS 稳。
- **易用性**：Windows 整合包成熟（解压即用，4G 显存起步，支持 50 系），B站教程密度全网最高。
- **失败模式**：训练集质量差时 v3/v4 线崩；多音字靠前端+.getActiveHost 仍有翻车案例；流式/服务化生态弱于 CosyVoice。

#### 3.3 IndexTTS-2/2.5（B站）——情绪+时长控制最全，注意权重协议

- **硬数字**：IndexTTS2 论文（[arXiv:2506.21619](https://arxiv.org/abs/2506.21619)，AAAI 2026）称 WER/SIM/情感保真同时超 F5-TTS/MaskGCT/CosyVoice/GPT-SoVITS；LibriSpeech-test-clean WER 3.115%、SIM 0.870。**2.5 技术报告**（[arXiv:2601.03888](https://arxiv.org/abs/2601.03888)，2026-01）Table 2：IndexTTS2.5（0.8B）test-zh WER 4.36/SS 77.10、test-en 5.12/68.06，平均 6.75/73.18，GRPO RL 后 6.00/73.63；RTF 相对 2.0 **提速 2.28 倍**（A10 上 T2S 0.232→0.119）；情感克隆 CV3-Eval Emotion-ZeroShot 准确率对 CosyVoice3 从 0.467 提到 0.713（zh）。
- **时长控制（对本项目有独特价值）**：IndexTTS2 是**第一个把"精确时长控制"做进自回归 TTS 的开源模型**——可以指定输出时长。配音场景里"合成音频塞回原字幕时间窗"是刚需，这一手能力 CosyVoice3 没有（只能靠变速对齐）。
- **显存**：2.5 版 0.8B 参数，官方整合包面向消费级卡（B站教程普遍 8-12G 显存起步，4090 富余）。
- **社区口碑**：中文克隆圈热度最高的"整合包之王"（B站相关视频动辄数万播放），liudon 横评里**完成度高但合成耗时明显最长（测试句 2 分钟以上，CosyVoice 同任务 24 秒）**——批量配音场景要掂量吞吐。
- **协议**：代码 Apache-2.0，**模型权重是 INDEX_MODEL_LICENSE（bilibili Model Use License）：商用需事先向 B站登记并取得书面授权；自用/研究无碍**（[GitHub issue 讨论](https://github.com/index-tts/index-tts/issues)、[HF IndexTeam/IndexTTS-2](https://huggingface.co/IndexTeam/IndexTTS-2)）。本项目自用，不踩线。

#### 3.4 ZipVoice（k2-fsa/小米）——轻量快速，SmartSub 同款本地引擎

- **硬数字**（[ZipVoice 论文 arXiv:2506.13053](https://arxiv.org/abs/2506.13053)，Seed-TTS-Eval）：
  - test-zh：SIM-o 0.751 / WER 1.40（ZipVoice 16NFE）；Distill-4NFE 0.748/1.39（真人基线 0.755/1.25）——**123M 参数做到这个数字，效率惊人**；
  - test-en：0.697/1.70（对比 CosyVoice2 0.652/2.57，F5-TTS 0.664/1.85）；
  - 速度：Distill-4NFE RTF **0.0125**（H20 GPU），比 F5-TTS 快 23.7 倍；CPU 单线程也能跑（RTF 1.22）。
- **工程特性**（[GitHub README](https://github.com/k2-fsa/ZipVoice)）：中英双语+混说；Apache-2.0；文本按标点自动分块、显存近常数；**多音字可手动拼音纠正**（`这把剑<chang2>三十公分`）；支持 TensorRT 导出再提速 2 倍；**ZipVoice-Dialog/Dialog-Stereo** 还能直接生成双人对话（本项目用不上但说明其对话数据功底）。
- **社区口碑**：1,071 star，学术圈（k2/新一代 Kaldi 系）口碑好，出圈度不如 CosyVoice/IndexTTS；**SmartSub v3.4.0 选它做本地声音克隆引擎**（[SmartSub v3.4.0 发布说明](https://github.com/buxuku/SmartSub/releases/tag/v3.4.0)），佐证其工程可靠性。
- **失败模式**：中文韵律偶尔有不自然停顿（[issue #169](https://github.com/k2-fsa/ZipVoice/issues/169)）；最后 push 2025-12，更新节奏放缓；克隆相似度 SS 略低于 CosyVoice3（0.751 vs 0.780，各自口径）。

#### 3.5 Kokoro v1.1-zh——**不是克隆模型**，预设音色的小钢炮

- **是谁训的**：hexgrad 旗下 @rzvzn 训练（个人/小团队，非官方大厂）；100 个中文说话人数据来自**龙猫数据（LongMaoData）**免费提供的专业录音棚数据（[HF 模型卡](https://huggingface.co/hexgrad/Kokoro-82M-v1.1-zh)）。
- **质量上限**：作者自己写明——**短期训练（120 A100 小时，约 110 美元成本）、仅 100+ 小时数据、"不是严格意义的升级版，发布是为了收集反馈"**。**无任何公开基准数字**，仅有社区口碑（"小而自然""本地部署神器"）。
- **对本项目的定位**：82M 参数、Apache-2.0、CPU 都能实时跑，适合**预设音色旁白/解说**这类不要求像谁的场合；**它没有 zero-shot 克隆能力（固定音色池）**，绝不能当"分人克隆"引擎用。

#### 3.6 edge-tts——预设音色路线首选，风控现状可控

- **音质口碑**：无基准（微软未开源模型），社区公认"免费 API 里最自然的中文音色之一"，zh-CN 音色全（晓晓/YunxiNeural 等），B站教程仍以"永久免费、快速稳定"为主流评价（[B站](https://www.bilibili.com)）。
- **403 风控现状（2026）**：2024-10 微软加 Sec-MS-GEC DRM token 后旧版全挂，rany2/edge-tts 已实现 token 生成，升级即修复（[issue](https://github.com/rany2/edge-tts/issues)）。2026 年剩余问题降级为**偶发**：[#473 间歇性 No audio received（open，2026-04 起）](https://github.com/rany2/edge-tts/issues/473)、[#482 WebSocket 503（2026-07）](https://github.com/rany2/edge-tts/issues/482)；**大陆 IP 触发限流的概率更高，社区标准做法是配代理**。结论：能用，但**必须做失败重试+本地 TTS 降级**（CosyVoice 预设音色兜底）。
- **限制**：不能克隆、商用条款灰色（微软未授权 API 化使用）、长句需要自己切分。

#### 3.7 中文配音场景结论清单

**克隆路线（本项目主路线）：**
- **首选：CosyVoice3-0.5B-2512（+RL 权重）**——开源里硬数字最好的中文克隆（CER 0.81~1.21 / SS 77~78），Apache-2.0 无协议坑，4~5GB 显存，4090 上 RTF<0.1，vLLM/TensorRT-LLM 服务化路径全，方言/情感指令都是加分项。代价：长文本必须分段合成（配音场景天然分段，无实际代价）。
- **次选 A：IndexTTS-2.5**——需要"精确时长控制"或"情绪复刻"的句子上它（时长控制对塞回字幕时间窗是真刚需）；自用无协议问题；批量吞吐慢是主要短板。
- **次选 B：GPT-SoVITS v2ProPlus**——某个说话人只有 1 分钟干净音频、又要求"像"到极致时，few-shot 微调它（RTF 0.014@4090，中文相似度社区口碑第一）；零样本直克隆不如首选稳。
- **轻量备选：ZipVoice-Distill（4 NFE）**——显存紧张/要批量吞吐时的性价比选项，数字好、Apache-2.0、多音字可纠。
- **避开**：F5-TTS（中文 SS 74.1/0.741 明显低于第一梯队，仅速度见长）；Kokoro v1.1-zh 当克隆用（没有克隆能力）；ChatTTS/OpenVoice（无克隆或克隆弱、已过时）。

**预设音色路线（不需要像原声，只要好听/清晰）：**
- **首选 edge-tts**（免费、自然、快），配本地 CosyVoice 内置音色做断网/风控降级；
- 轻量本地备选 Kokoro v1.1-zh（zf_001 等 100 个中文音色，CPU 可跑）。

### 4. audio-separator + 分离模型——放心用，选 Mel-Roformer

**audio-separator（nomadkaraoke/python-audio-separator）**：把 UVR 的 MDX-Net/VR/Demucs/MDXC/Roformer 全系模型包成 Python 库 + CLI，pip 可装，CUDA 11/12 Docker 齐全（[GitHub README](https://github.com/nomadkaraoke/python-audio-separator)）。

**人声分离模型硬数字**（库自带 `models-scores.json`，MVSEP 口径音乐测试轨人声 SDR 中位数，我按库内数据算的中位数排名）：

| 模型 | 人声 SDR 中位数 | 说明 |
|---|---|---|
| **vocals_mel_band_roformer.ckpt** | **12.60** | 库内最高 |
| melband_roformer_big_beta4/beta5e | 12.44~12.52 | 社区迭代版 |
| model_bs_roformer_ep_368_sdr_12.9628 | 12.10 | BS-Roformer 经典款 |
| htdemucs_ft.yaml | 10.79 | Demucs v4 微调版 |
| MDX23C-8KFFT-InstVoc_HQ | 10.56 | MDX23C 代表 |
| MDX23C-8KFFT-InstVoc_HQ_2 | 10.51 | |
| UVR-MDX-NET 系 / Kim_Vocal_2 | 10.2~10.4 | 上一代 |

（来源：[audio-separator models-scores.json](https://github.com/nomadkaraoke/python-audio-separator/blob/main/audio_separator/models-scores.json)；社区情报库 [deton24 分离模型指南 2026-03 版](https://github.com/nomadkaraoke/python-audio-separator/blob/main/docs/deton24-audio-separation-info-2026-03-15.md)同样口径："Roformer 系 SDR 普遍 10-17，是当前质量最好的架构"。）

**采访类场景选型：**
- **主分离：`mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956.ckpt` 或 `vocals_mel_band_roformer.ckpt`**。Karaoke 款的特长是"主唱 vs 背景和声"的分离（SIR 高达 28，库内数据），对应到采访里就是"人声 vs BGM 里的人声残留"，正对需求；通用 vocals 款 SDR 最高。两者任选，先用通用款即可。
- **htdemucs_ft / MDX23C 为什么不选**：SDR 低约 2dB，且 htdemucs 是 4-stem 模型（鼓/贝斯/其他/人声），我们只要两轨，浪费算力。它们不是不能用，是被 Roformer 全面替代。
- **去混响要不要**：**条件性要**。可用 `dereverb_mel_band_roformer_less_aggressive_anvuew_sdr_18.8050.ckpt`（温和版，SDR 18.8）或 Sucial `dereverb-echo_mel_band_roformer_sdr_13.4843_v2.ckpt`（去混响+回声）。判据：采访在会议室/家里录、有明显房间混响 → 人声轨过一遍再进 ASR/TTS 参考提取；录音棚级干声 → 跳过（分离本身会引入轻微伪影，能少一步就少一步）。

**"BGM 垫底轨精度要求不高"的论证**：本项目分离的目的不是拿干净的 BGM 二创，而是**把 BGM 压低（比如 -12 ~ -18dB）垫在配音下面**。人声分离模型的典型失败模式是"人声里漏进一点 BGM 高频、BGM 里残留一点人声"——压低混回后：BGM 侧残留的人声被 -12dB 以上衰减，掩蔽效应（配音人声的存在）下基本不可闻；BGM 高频缺失用一点 EQ/激励就能糊弄过去。所以单模型单遍分离完全够，**不需要 MVSEP 式多模型集成**（那是做卡拉OK原声提取的极致需求）。真正要精的是人声轨（要拿去做克隆参考+ASR），这正好是 Roformer 的强项。

### 5. WhisperX + faster-whisper（备选 ASR 线）——放心用

- **large-v3 WER**：Open ASR Leaderboard（[HF leaderboard](https://huggingface.co/spaces/hf-audio/open_asr_leaderboard)、[论文 arXiv 2025-12](https://arxiv.org)，60+ 系统/10 数据集）上 whisper-large-v3 英文综合 WER 约 **7.44%**（[Vexascribe 2026-05 分析](https://vexascribe.com)），已被 Parakeet/Canary 系（<6%）反超但仍是**多语言通用性最好的开源模型之一**；LibriSpeech clean 约 2.7%。中文场景 large-v3 仍是 Whisper 系最佳（turbo 版保留约 95% 精度、快 4 倍，追求吞吐可换）。
- **对齐精度**：Whisper 原生 segment 时间戳"可差数秒"，WhisperX 用 wav2vec2 强制对齐做到**词级时间戳**（[WhisperX README](https://github.com/m-bain/whisperX)）；官方明说"更大的对齐模型没发现更有用"，中文会自动选 HF 上的中文 wav2vec2 模型。已知局限：数字/符号可能对不上时间戳、**重叠语音处理弱**（官方原话"not handled particularly well"）——重叠段的词归属要靠 pyannote 侧互补。
- **3090 实测速度**：RTF≈0.08，**1 小时音频约 4.8 分钟**（large-v3 + 批处理，[gigagpu 3090 基准 2026-04](https://gigagpu.com)）；论文理想条件 70 倍实速（[WhisperX 论文](https://arxiv.org)）。24GB 显存富余，batch_size 可给大。
- **与流水线的关系**：本项目字幕源是 OCR（画面里已有字幕），ASR 线是字幕不可用/需要英文字幕辅助归人时的备胎。WhisperX 的价值在"ASR+词级对齐+pyannote diarization 一站式"，跟 OCR 字幕时间窗互补校验。

### 6. SmartSub（buxuku/SmartSub）——当对照品和应急备胎，不当生产件

**项目状态：活跃，月更。** v2.16.0（2026-06-10）→ v3.x 连发：v3.1/3.0（2026-06-23 多引擎）→ v3.4.0（2026-07-16 **配音+声音克隆**）→ v3.5.0（07-23 在线视频下载）→ v3.6.0（07-30 AI 字幕精修）→ **v3.7.0（2026-08-06 多角色配音与说话人识别）** → v3.8.0（2026-09-10 多格式导出/备用服务容灾）（[Releases](https://github.com/buxuku/SmartSub/releases)）。

**功能覆盖核实**（发布说明原文）：
- v3.4.0：TTS 配音（行级试听/调整/重生成）；配音服务商全家桶（Edge TTS/OpenAI 兼容/Azure/ElevenLabs/火山豆包+本地引擎）；**声音克隆三选一：本地 ZipVoice、火山复刻、ElevenLabs 即时克隆**；音色降噪+质量检测。
- v3.7.0：**字幕说话人区分（自动识别发言者并标注角色）**；按角色批量分配音色+单句覆盖；参考文稿高置信匹配对齐；多卡指定 CUDA。

也就是说，**"ASR→分人→按角色配音→本地 ZipVoice 克隆"这条链 SmartSub 已经全部内置**，和本项目需求高度重叠（差异：它走 ASR 不走 OCR 字幕、不做 BGM 分离混音、无"独立音频+垫底轨"导出理念）。

**Issue 区高频问题**（45 个 open issue 里最响的）：
- [#130 CUDA 使用情况集中反馈（27 评论）](https://github.com/buxuku/SmartSub/issues/130)、[#378 一直在用核显](https://github.com/buxuku/SmartSub/issues/378)、[#424 国内模型能否支持 CUDA](https://github.com/buxuku/SmartSub/issues/424) —— GPU 加速路径混乱是最大痛点；
- [#418 克隆音色时闪退（2026-08）](https://github.com/buxuku/SmartSub/issues/418) —— 克隆功能（v3.4 才加）仍在稳定期；
- [#402 模型基本全试过，几乎无法使用（2026-07）](https://github.com/buxuku/SmartSub/issues/402)、[#454 转录夹杂其他语言](https://github.com/buxuku/SmartSub/issues/454)、[#409 47b 字幕一行 trolls（幻觉）](https://github.com/buxuku/SmartSub/issues/409)、[#451/#442 Qwen3-ASR 输出内部模板残留](https://github.com/buxuku/SmartSub/issues/451) —— ASR 引擎扩展后质量参差；
- [#437 中文 SRT 在 Win11 乱码](https://github.com/buxuku/SmartSub/issues/437)。

**当生产件靠不靠谱**：单人自用、需求恰好落在它的功能面上（字幕→翻译→多角色配音），**能跑通且省开发量**；但它是 GUI 黑盒——字幕源只能 ASR（不能吃 OCR 字幕）、时间窗归人策略不可编程、时长对齐细节（变速/静音填充策略）不可控、批量自动化无 API（[#163 有命令行功能请求](https://github.com/buxuku/SmartSub/issues/163)还开着）。**结论：本项目按 01 方案自建轻管道；SmartSub 留作两用——(a) 给非技术流程当 GUI 应急工具，(b) 当行为参照（它的"行级试听+重生成"交互值得抄）。自建替代成本不高：本报告每个组件都有明确调用方式，管道五段全是 pip 级依赖。**

## ④ 开发时的具体调用建议

### OCR 字幕（首选自建，备选 VideOCR）
- 自建管线：OpenCV 抽帧（2~4 fps 起步，检测到字幕区变化时加密）→ 裁字幕区（底部固定 ROI + 可选顶部黑名单区防台标）→ **PaddleOCR `PP-OCRv4_server_rec`（或最新的 PP-OCRv5）中文模型** → 相邻帧文本相似度合并成行（编辑距离>0.2 即换行）→ 行起止=首末命中帧时刻（用抽帧间隔做插值平滑）。PaddlePaddle 用 GPU 版注意和 CUDA 版本配套（4090 用 CUDA 12.x 配套 wheel）；嫌 Paddle 环境烦就换 RapidOCR（同一套模型的 ONNX 版，pip 即装）。
- 交互式抽查/兜底：**timminator/VideOCR**（GUI 框字幕区，CLI 可批处理，CUDA 12.9 版适配 4090/50系）。

### 声纹分人
```python
from pyannote.audio import Pipeline
pipeline = Pipeline.from_pretrained(
    "pyannote/speaker-diarization-community-1",
    token=os.environ["HF_TOKEN"])   # hf.co/settings/tokens 生成 read token，先在模型页点接受协议
pipeline.to(torch.device("cuda"))
output = pipeline("mono16k.wav", min_speakers=1, max_speakers=6)  # 采访不确定人数时给宽范围
# output.speaker_diarization 迭代 (turn, speaker)
```
- 输入转 mono 16kHz（ffmpeg `ffmpeg -i in -ac 1 -ar 16000 out.wav`）。
- 分人前先过人声分离的人声轨，BGM 重的采访 diarization 明显更稳。
- 归人策略：OCR 字幕时间窗与 speaker turn 取重叠最大者；重叠段（一个窗压两个 speaker）标记出来人工抽查。

### TTS（主：CosyVoice3；副：IndexTTS-2.5 / GPT-SoVITS v2ProPlus）
- 权重：`modelscope snapshot_download('FunAudioLLM/Fun-CosyVoice3-0.5B-2512', local_dir=...)`，RL 权重同仓库；代码 `git clone https://github.com/FunAudioLLM/CosyVoice --recursive`。
- 参考音频：每个说话人从分离后的人声轨挑 3~10 秒干净段（ZipVoice/CosyVoice 官方都建议 3 秒起步、太长反而慢且降质）。
- **逐句合成（对齐字幕行），单句别超 50 字**——长文本错乱是 CosyVoice2 起的已知坑，配音场景按字幕行切句天然规避。
- 克隆参考文本必须和参考音频严格一致（错一个字相似度掉）。
- 需要时长控制的句子走 IndexTTS-2.5（`hf download IndexTeam/IndexTTS-2.5`）；想为固定演员做精品音色走 GPT-SoVITS v2ProPlus 微调（1 分钟素材起步）。
- 多音字保险：ZipVoice 支持 `<chang2>` 手工拼音；CosyVoice 系用 ttsfrd 前端，个别翻车句可改写文本绕开。

### 人声/BGM 分离
```python
from audio_separator.separator import Separator
sep = Separator(output_single_stem=None, sample_rate=44100)
sep.load_model("mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956.ckpt")  # 或 vocals_mel_band_roformer.ckpt
voc, bgm = sep.separate("full_audio.wav")   # BGM 轨压 -12~-18dB 垫底
# 房间混响明显时，对 voc 再过一遍：
sep.load_model("dereverb_mel_band_roformer_less_aggressive_anvuew_sdr_18.8050.ckpt")
```

### ASR 备线
```
pip install whisperx
whisperx audio.wav --model large-v3 --language xx --diarize \
  --hf_token $HF_TOKEN --batch_size 16 --compute_type float16
```
- 3090 预算：1 小时音频约 5 分钟（RTF 0.08 实测口径）；输出词级时间戳，可和 OCR 字幕窗互校。

### 显存调度（3090 24G / 4090x2 48G）
- CosyVoice3 稳态 ~4-5GB、pyannote ~2-4GB、Whisper large-v3 ~8GB、Roformer 分离 ~3-5GB——**单 3090 就能串行跑全管道**；4090x2 可把"TTS 合成"和"OCR+分离"分卡并行。全流程 1 小时采访视频预计 20-40 分钟内（TTS 逐句合成是大头，按 RTF 0.1~0.3 估）。
